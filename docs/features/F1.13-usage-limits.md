# F1.13 — Daily usage limits

**Sources:** PRD §20.6, DB Design §4.17 / §4.19 / §7.5, API Design §7.2 / §11 / §13.1.

## What it does

Protects AI and rendering costs with per-user caps per **IST day** (no billing in V1):

| Counter | Default per day |
|---|---|
| `storyboards` | 20 |
| `revisions` | 100 (plus 50 per project, enforced with `projects.revisionCount` in F7) |
| `builds` | 15 |
| `renders` | 10 |
| `illustrations` | 40 |
| `voiceCharacters` | counted (cost tracking), no limit |

Nothing consumes these yet: storyboard generation (M2), revisions (M3), builds (M4), renders (M4) and illustrations call the shared check when they arrive. This feature builds that check and the read endpoint.

## Behaviour

- **Day:** the date in Asia/Kolkata (`YYYY-MM-DD`); everything resets at IST midnight (`resetsAt` = 18:30 UTC). Documents expire 40 days after their day (TTL on `expiresAt`).
- **Check and count atomically** (§7.5): first make sure today's document exists (an upsert on exactly `{ userId, date }`, which MongoDB retries itself if two first requests race), then one update **without upsert** increments the counter only while it stays within the limit; matching nothing means the limit is reached. Two requests at once can't both pass the last slot, and no step can fail with a duplicate key, so it can join the transaction that starts the work (§6.2): a write error would abort that transaction.
- **Amounts** must be positive whole numbers (anything else is a programming error). A stored counter that isn't a number is an error, never reported as "limit reached".
- **Limit reached:** `429 LIMIT_REACHED`, `details: { counter, limit, used, resetsAt }`, `Retry-After` until the reset, and the message "You've reached today's limit for renders. It resets at midnight (IST)." Nothing is counted.
- **Limits come from** the defaults above, then the `limits` entry in the `config` collection (admin-wide, read through a 60-second cache), then the user's `profiles.limitsOverride` (per user, admin).
- **`GET /api/v1/me/usage`** → `{ date, resetsAt, counters: { storyboards: { used, limit }, revisions, builds, renders, illustrations } }`.
- **Headers:** limited endpoints will send `RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset` (a helper is provided).
- **UI:** per PRD §20.6, limits are shown only when approached, so there is no usage panel; the screens that start work (M2–M4) will read `/me/usage`.

## Fix to the §7.5 pattern

The single upsert with filter `{ userId, date, [counter]: { $lt: limit } }` has two problems. It doesn't match a day document that exists but has **no field yet for this counter** (e.g. a render after a storyboard today), so the upsert hits the unique `{ userId, date }` index and looks like "limit reached". And it uses that duplicate-key error as the "limit reached" signal, which **aborts the caller's transaction** (the request then fails or hangs instead of answering 429). So: ensure the day's document first, then increment without upsert; the filter also accepts a missing counter (`$exists: false`).
