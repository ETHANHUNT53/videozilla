# F1.14 — Cross-user security tests

**Sources:** System Design §13.2, API Design §1 (principle 3) and §17 (security checklist), DB Design §1 (`userId` on every document).

## Goal

Prove, in CI, that a signed-in user (B) can't read, change, delete, restore or copy another user's (A's) data through any `/api/v1` route, and that the answer for someone else's id is exactly the answer for an id that doesn't exist (`404 NOT_FOUND`, never `403`), so it doesn't even reveal that the item exists.

## How

One integration test file (`apps/web/src/server/security/cross-user.test.ts`) on a throwaway MongoDB with the real migrations:

1. **Two users with data:** A has live, deleted and needs-attention projects, idea sessions, a profile with non-default settings and usage counts; B has a project of their own.
2. **Every handler, as B, against A's data:**

| Route | Checked |
|---|---|
| `GET /projects/{A}` | 404, same body shape as an unknown id |
| `PATCH /projects/{A}` (with and without `If-Match`) | 404; A's project unchanged (title, settings, `rev`) |
| `DELETE /projects/{A}` | 404; not deleted, A's jobs not cancelled |
| `POST /projects/{A deleted}/restore` | 404; stays deleted |
| `POST /projects/{A}/duplicate` | 404; no copy for anyone, no idea session copied |
| `GET /projects` (every filter, A's title as search, A's cursor) | only B's projects |
| `POST /projects` with a `userId` in the body | 400 (strict schema); never creates for A |
| `GET /me`, `GET /me/usage`, `PATCH /me/profile` (incl. `userId` / `role` in the body) | only B's own data; 400 for smuggled fields; A untouched |

3. **No route is forgotten:** the test lists the route files under `src/app/api/v1` and fails if one isn't in its coverage table, so a new endpoint must come with its cross-user case.
4. **Also:** every route answers `401` without a session, and `403 EMAIL_NOT_VERIFIED` for an unverified user (except `GET /me`, which works before verification).

Page-level reads (project page, Settings, Welcome) use the same repository functions (`getProject`, `getOrCreateProfile`, `needsWelcome`), which are covered through the routes plus direct checks.

Out of scope: `/api/auth/*` (Better Auth's own session handling) and `/api/inngest` (signed by Inngest).
