**Sources:** PRD F3 (F3-FR1, structure rules, edge cases), §11 lifecycle, §13.2–13.4 (prompting, storyboard schema with `beat` / `themeHints`, validation and repair), §14.2 scene catalog, §14.6 themes, F4-FR9 / F4-FR10 (theme switch never regenerates the script; new themes need no schema change), §15.2 duration targets, §16.1 P1 / §16.3–16.5 (pipeline, retries, timeouts, progress messages), §20.6 (storyboards 20/day); [M2 design §2 row 8, §5](../M2_DESIGN.md); DB Design §4.3, §4.6, §4.14, §5.1–5.3, §6.2, §6.3, §7.2, §7.5, §7.6; API Design §10, §12, §13.4, §13.7, §15, §16. Built on the M0 storyboard schema and validator (`packages/schema`, `packages/pipeline`) and the F2.x AI chain (`generateJson`: Gemini → Groq → OpenRouter, mock provider, `ai_calls`, refunds).

## What you'll see

1. In the Idea Studio, once a brief exists, **Generate storyboard →** is live.
2. You press it. The right column shows a **progress card** instead of the button:
   - *Reading your brief…* → *Writing your script and planning scenes…* → *Checking scenes, sync and length…* (→ *Adjusting the length…*, only when needed) → *Saving your storyboard…*
   - each step pending / running / done, plus "Usually 20–40 seconds. You can leave this page; it keeps going."
3. While it runs, the idea, brief, chat and settings are **read-only** (the video is `storyboard_generating`; the Library chip says so too).
4. **When it's done:** the stepper moves on to Storyboard and **Next: Storyboard →** is live. It opens a **simple "Storyboard ready" page**: title, hook, scene count, estimated length, the chapters, and the scenes as a plain list (number, role, chapter, narration, scene type). The real storyboard screen with animated scene cards is F3.3 and replaces this page.
5. **If it fails:** the card says why in plain words (AI busy, unusable reply, refused topic), that it **didn't count** against today's limit (see Q3), and offers **Try again**. Your idea and brief are untouched; the video goes back to where it was.
6. **Regenerate:** from a ready storyboard, the Idea step's button reads **Regenerate storyboard**, with a confirm ("Makes a new version; the current one is kept"). The new storyboard becomes version 2, 3, …

## API

### `POST /api/v1/projects/{id}/storyboard/generate` → `202`

- **Body** (strict): `{}` from `idea_draft`, or `{ "regenerate": true }` from `storyboard_ready`.
- **Needs a brief:** none yet → `422 VALIDATION_FAILED`, field `brief`, "Make a brief first."
- **In one transaction** (DB §6.2):
  1. count one `storyboards` unit (`consumeUsage(…, { session })`; `429 LIMIT_REACHED` at the limit, nothing else written);
  2. move the project to `storyboard_generating` (compare-and-set on the status it was read with; `rev` + 1, `statusChangedAt`);
  3. insert the `pipeline_runs` document: `kind: "storyboard"`, `status: "queued"`, `active: true`, `trigger: { by: "user", storyboardVersion: <current or null> }`, the 4 steps as `pending`, `idempotencyKey: "{projectId}:storyboard:{runId}"`, and the event in `outbox` (DB §7.6), plus `usage: { date, amount }` so the job can give it back.
- **After commit:** the `storyboard/requested` event `{ runId }` is sent (event id = the run's key, so a re-send is a no-op), then `outbox.sentAt` is set.
  - **No job runner reachable** (local development without `npm run jobs`): like account deletion, the job runs **in this server process** right after the response (Next's `after()`), with the same code and steps.
  - **In production**, a failed send fails the run at once (`JOB_NOT_STARTED`), gives the unit back and moves the video back, so nothing is left hanging.
- **Response:** `202 { run, project }` (`project.status: "storyboard_generating"`), `Location: /api/v1/projects/{id}/status`.
- **Double click / second tab:** while a storyboard run is active, the same `202 { run, project }` comes back with `Idempotent-Replayed: true`; nothing is counted twice. (The partial unique index `active_per_kind` stays the last line of defence.)
- **Errors:**
  - `404` unknown or someone else's video (the F1.14 cross-user check gets the new routes);
  - `409 INVALID_STATE`: any status other than `idea_draft` / `storyboard_ready`, or `storyboard_ready` without `regenerate: true` (so an old tab can't replace a storyboard by accident);
  - `422 VALIDATION_FAILED` (no brief), `429 LIMIT_REACHED`, `400` bad body.

### `GET /api/v1/projects/{id}/status`

`200 { project: { id, status, rev, exportOutdated, attention, currentStoryboardVersion }, activeRuns: Run[], lastRuns: Run[] (≤ 5, newest first), renderQueue: null, pollAfterMs: 2000 | null }` (API §13.7, Run shape §10.2: `steps[]` with `label`, `status`, `attempt`; `progress` 0–100; `error { code, message, retryable, step }`).

- `pollAfterMs` is `null` when nothing is active: the page stops polling.
- **Stuck runs** (no watchdog until F10): a storyboard run that hasn't moved for **5 minutes** (the job died with the server, say) is failed here with `JOB_STOPPED`, its unit given back and the video moved back, so a video can never stay "generating" forever.

### `GET /api/v1/projects/{id}/storyboard`

`200 StoryboardVersion` (API §12: `version`, `source`, `storyboard`, `estimatedDurationSec`, `wordCount`, `warnings`, `isCurrent`, …), or `404` before the first one. Used by the result page now and by F3.3 later.

## The job: `storyboard.generate` (Inngest, event `storyboard/requested`)

One function, concurrency 1 per project. Its steps are plain functions, so Inngest (`step.run` each) and the inline fallback run the same code. Each step updates `pipeline_runs.steps[]` (status, `startedAt`, `finishedAt`) and `run.progress`, which is what `/status` shows.

| # | Step (`name`) | Label (PRD §16.5) | What it does |
|---|---|---|---|
| 1 | `load_context` | Reading your brief… | Run still active? Project not deleted? Loads the brief, the settings (language, length, audience, board or exam), the creator's "what I teach", and the notes when the brief came from notes. |
| 2 | `write_script` | Writing your script and planning scenes… | **T4** through `generateJson` (the chain, one repair round per tier, fall-through, `ai_calls` with task `storyboard`, `projectId`, `runId`), temperature 0.5, deadline 75 s. |
| 3 | `check` | Checking scenes, sync and length… | Validation and repair (below). If the length is off by more than 15 %, **one** length fix (**T7**, task `length_fix`, deadline 45 s): the whole storyboard goes back with "tighten / expand to N–M words, keep the shape, ids, chapters and cues"; the result is validated again and the one closer to the word budget is kept. Still off → saved with a warning (the F3.3 duration chip, F3-FR9). |
| 4 | `save_version` | Saving your storyboard… | One transaction (DB §6.3, below). |

- **At most 2 AI requests per generation** (each with its own repair round and chain); one `storyboards` unit in total.
- **Retries:** `generateJson` already retries a busy model and falls through the chain. Inngest retries a step that crashed (database hiccup) up to 2 times; an AI answer (busy, unusable, refused) is final for that run, and you press Try again.
- **Timeouts:** the `/api/inngest` route gets `maxDuration = 120` s (a step must fit in one function call on Vercel; needs Pro for > 60 s, as PRD §16.4 already says).
- **Deleted or cancelled meanwhile:** before saving, the run must still be active and the project still `storyboard_generating`; otherwise the result is dropped and the unit given back.

### On failure

- The run becomes `failed` with `error { code, message, retryable: true, step }`:
  `AI_BUSY` ("The AI is busy right now. Try again in a minute."), `AI_UNAVAILABLE` (every provider needs a person: credits / key), `AI_OUTPUT_INVALID` ("The AI couldn't write a usable storyboard this time."), `UNSAFE_CONTENT` (the model refused), `JOB_NOT_STARTED`, `JOB_STOPPED`, `INTERNAL`.
- **The video goes back** (DB §5.1, API §16): to `idea_draft` when it had no storyboard, to `storyboard_ready` (the previous version kept) on a regenerate. `attention` stays empty: in the DB design it belongs to `needs_attention` only (see Q4).
- **The unit is given back** (`refundUsage`) for every failure except a refusal (see Q3), the same rule as the idea AI.

## Storyboard schema (theme-neutral, extensible)

`packages/schema` grows from the M0 shape to PRD §13.3. Everything below is **content**; nothing names a colour, font, layout or character. Any theme reads what it wants and ignores the rest (F4-FR9).

```ts
Storyboard {                        // stored in storyboard_versions.data (≤ 100 KB), schemaVersion 1
  language: "en" | "hi"
  targetDurationSec: 60 | 90
  title: string                     // ≤ 70 chars
  hook: string
  social: { caption: string /* ≤ 2,200 */; hashtags: string[] /* 5–15 */; coverText: string /* ≤ 5 words */ }
  scenes: Scene[]
}

Scene {
  id: string                        // "s1", "s2"… set by our code, never by the AI (§13.2)
  role: "hook" | "explain" | "example" | "recap" | "outro"
  narration: string
  type: SceneType                   // the M0 renderer's catalog today (TitleHook, KeywordReveal, BulletSteps, Flowchart,
                                    // Comparison, StatCounter, RecapOutro, Illustration, UnitGrid); M3 adds the rest of §14.2
  props: object                     // checked by that type's Zod schema
  cues: Cue[]                       // { target, anchor, occurrence? }
  section: string                   // short eyebrow label ("how it works"), from M0
  beats: HeadlineBeat[]             // 1–3 on-screen headlines per scene, from M0 (text content; any theme may show them)
  beat: BeatMeta                    // NEW: the scene's place in the story (below), always filled after validation
  themeHints?: Record<ThemeId, unknown>  // NEW: optional per-theme extras; never written by this generation
}

BeatMeta {
  chapter?: { index: number; headline: string; subhead?: string }   // hook and recap/outro have none; body scenes all do
  mood: "curious" | "explain" | "problem" | "solution" | "recap"
  diagram?: { id: string; step: number }   // this scene adds step N to a diagram that stays on screen across scenes
}
```

**Naming:** `beats` (plural, M0) are the headline lines a scene shows; `beat` (singular, new) is the scene's structure. The M0 field keeps its name, so the M0 renderer and fixtures don't change. The code comments and this note say which is which.

**Why this is extensible (F4-FR10):**
- `beat` describes the *story* (which chapter, what it feels like, which diagram step), which every theme can map to its own look: Mentor turns chapters into its numbered header and progress bar, `mood` into a presenter pose (`curious` → think, `problem` → alarm, `solution` → point, `explain` → explain, `recap` → arms crossed), and `diagram` steps into its central diagram. Midnight can ignore all of it, or show the chapter as its section label.
- `themeHints` is an open map keyed by theme id (`^[a-z][a-z0-9-]{1,31}$`), each value ≤ 2 KB of JSON. The storyboard schema never lists theme ids or their fields, so **adding a theme never changes this schema or the stored versions**. A theme that needs hints declares its own hint schema in the M3 theme registry; hints are derived later by that theme's cheap step (§14.6.3) and checked by its schema then. Until a theme registry exists, unknown keys are kept as they are (within the size limit) and never read.
- No script is ever regenerated for a theme: generation writes only theme-neutral data, and `themeHints` is filled per theme on demand.
- The theme itself (`styleId`, default `midnight`) stays a project setting and isn't part of the storyboard.

## The prompt (`packages/ai/src/storyboard.ts`)

- **System prompt** = the proven M0 storyboard prompt (scene catalog, sync-cue rules, headline rules, Hindi rules, "show, don't just tell"), updated to PRD §13.2–13.3 and with a new **STORY STRUCTURE** part:
  - **chapters:** the body scenes are grouped into 2–3 chapters (~60 s) or 3–4 (~90 s), in teaching order, usually one per brief key point; each chapter has a headline of ≤ 5 words (≤ 6 in Hindi) and an optional subhead; the hook and the recap/outro have no chapter;
  - **mood** for every scene: `curious` (a question or surprise), `explain`, `problem` (a difficulty, myth, danger), `solution` (the answer, the fix), `recap`;
  - **diagram:** when the topic is a process or system, one central diagram (`id` like `"main"`) that grows step by step across the body scenes (`step` 1, 2, 3…); otherwise none;
  - the video's language, length (word budget from §15.2) and scene count (Q1); no theme, colour or layout words.
- **User prompt:** the brief (title, hook, angle, audience, key points, left out), the audience and board or exam, the creator's "what I teach", and the notes (≤ 20,000 chars) when the brief came from notes ("use only facts from the notes", as F2.4). All of it inside delimiters with `asData`, as data, never instructions.
- **Reply:** `RawStoryboard` (with `beat` per scene) or the usual refusal `{ refused, category }`.
- **Mock (`AI_PROVIDER=mock`):** `mockStoryboard(input)` builds a valid storyboard from the brief in English or Hindi, inside the 60 / 90 s word budget, with chapters, moods and one diagram, and "[Mock]" in the hook. Triggers in the brief title: `[mock:busy]`, `[mock:refuse]`, and `[mock:long]` (a script that's too long, to exercise the length fix).

## Validation and repair (`packages/pipeline/src/validate.ts`, PRD §13.4)

The M0 validator keeps doing what it proved (unknown type → KeywordReveal, props clamped and checked, cues to unknown elements dropped, anchors checked against the narration, headline beats defaulted, ids `s1…sN`) and gains:

1. **Schema:** Zod; one repair round with the errors (in `generateJson`), else the next model, else `AI_OUTPUT_INVALID`.
2. **Structure:** scene count within 6–12 (~60 s) / 8–16 (~90 s); first scene `hook`; last `recap` / `outro` as RecapOutro; 8–40 words per scene; no more than 2 of the same type in a row. Out of range → a warning (and it feeds the length fix), not a failure.
3. **`beat` repairs** (never a failure):
   - missing or unknown `mood` → from the role (`hook` → curious, `explain` / `example` → explain, `recap` / `outro` → recap);
   - chapters: dropped on the hook and recap/outro; a body scene without one joins the chapter before it (the first body scene starts chapter 1); chapter numbers are renumbered 1, 2, 3… in scene order, a chapter keeps the headline it first appeared with (cut to ≤ 40 chars), and no headline at all → the scene's `section`; more than 5 chapters → the last ones are merged;
   - diagram: ids cleaned to a short slug, at most 2 diagrams per video (more → dropped), steps renumbered 1, 2, 3… per diagram in scene order (≤ 8 steps).
   Each repair is listed in `validationReport.repairs`.
4. **`themeHints`:** removed from AI output (generation is theme-neutral); the schema accepts them for later.
5. **Social:** hashtags cleaned (`#` added, duplicates removed, 5–15 kept), caption ≤ 2,200 chars, cover text ≤ 5 words.
6. **Length:** words ÷ WPM (EN 150, HI 140) + pauses, against §15.2; > 15 % off → the one length fix in the job step.
7. **Safety:** the model's refusal; the brief already passed the idea step's checks.

## Saving a version (F3.2, DB §6.3)

One transaction, after the AI calls (never inside):
- `storyboard_versions` insert: `version = (currentStoryboardVersion ?? 0) + 1`, `schemaVersion: 1`, `data`, `source: "generate"`, `basedOnVersion` (null the first time), `changeSummary` ("First storyboard" / "Regenerated from the brief"), `changedSceneIds` (all), `validationReport { repairs, warnings, wordCount, estimatedDurationSec }`, `model` (and provider);
- `projects`: compare-and-set on `status: "storyboard_generating"` → `storyboard_ready`, `currentStoryboardVersion`, `statusChangedAt`, `rev` + 1;
- `pipeline_runs`: `succeeded`, `active: false`, steps done, `finishedAt`.
- The unique `{projectId, version}` index makes a concurrent save fail cleanly (retried once). Versions beyond the newest 30 are pruned (never the current one, DB §4.6).
- No migration: both collections, their validators and indexes are in `001_initial_schema`; account deletion and project purge already cover them.

| `storyboard_ready` | Regenerate | `storyboard_generating` |

| `storyboard_generating` | failed / stuck / not started, earlier version | `storyboard_ready` (earlier version stays current) |
| `storyboard_generating` | video deleted | (soft delete cancels the run, as today) |

`allowedActions` already follows DB §5.2: during `storyboard_generating` only rename, delete and duplicate.

## The brief afterwards

The brief stays in the idea session exactly as it was. It's read-only while generating; in `storyboard_ready` it can be edited again (as today), and edits only affect the **next** regenerate; the saved storyboard never changes because of them (see Q5).

## The page

- `idea-step.tsx`: the **Generate storyboard →** button (enabled with a brief, `idea_draft`, no AI request running, not editing the brief) → POST, then the progress card; **Regenerate storyboard** with a confirm in `storyboard_ready`.
- A small `useRunStatus(projectId)` hook polls `/status` every `pollAfterMs` while something is active, pauses while the tab is hidden, and refreshes the project when a run finishes.
- `project-view.tsx`: **Next: Storyboard →** enabled once `currentStoryboardVersion` exists → `/projects/{id}/storyboard`.
- `/projects/{id}/storyboard` (new, minimal, server-rendered from the current version): header (title, hook, language, ~duration, word count, scene count), chapters, scene list, warnings, "Back to idea". F3.3 replaces its contents.
- Limit reached → the existing limit message and lock (as the idea AI).
