# F2.5 — Idea chat: refine the brief by chatting

**Status:** design **approved 2026-10-19** (answers at the end: 1,000 characters, other angles kept, 1 request each with failures refunded). **Built 2026-10-19** ([what was built](#built-2026-10-19)). Not checked live yet (your step).

**Sources:** PRD F2-FR5 (chat under the brief, each reply updates the brief in place with the changes highlighted), F10-FR1 (unsent chat text kept locally), F1 edge case (unsent chat text survives a sign-out), §20.6 (the shared `ideas` limit), task T3 (`llm.fast`, ≤ 8 s); [M2 design §2, §4](../M2_DESIGN.md) (approved: idempotent on `clientMessageId`, chat drafts in local storage); API Design §9, §12 (`ChatMessage`), §13.3 (`GET` / `POST …/idea/chat`); DB Design §4.5, §5.7, §7 (`chat_messages`, its indexes already exist). Built on F2.3 / F2.4: the same brief card, title rule, provider chain, limit, refunds and errors.

## What you'll see

1. **Once a brief exists**, a chat box sits under the brief card: *"Ask for a change — e.g. make it for kids, focus on the second point"*.
2. **You send a message**, the AI answers in a sentence or two, and **the brief changes in place**. The fields it changed (title, hook, angle, audience, a key point, "Left out…") are **highlighted** until your next message.
3. **When it can't tell what you mean**, it asks back (no change); **when you ask for something the brief can't hold** ("change the font", "make it 3 minutes"), it says so and where to do it (no change).
4. **The thread is saved with the video**: after a reload you see the conversation and the current brief.
5. **Unsent text is kept** in this browser if you leave or get signed out (PRD F10-FR1), per video.
6. The video's **title follows the brief title** while you haven't named it yourself, as with every brief (F2.3).
7. Everything else as before: one AI request at a time, the daily limit lock and messages, "busy" / "unavailable" / refusal messages.

## API

### `POST /api/v1/projects/{id}/idea/chat`

- **Body** (strict): `{ clientMessageId, content }`.
  - `clientMessageId`: a UUID v4 the page makes per message (API Design §9).
  - `content`: 1–1,000 characters after trimming (Q1), no control characters.
- **Needs a brief:** without one, `400 VALIDATION_FAILED`, field `brief`, "Make a brief first, then refine it here."
- **Response `200`:** `{ userMessage, assistantMessage, brief, briefUpdatedAt, project }`.
  - `userMessage`, `assistantMessage`: `ChatMessage` resources (thread `idea`). The assistant's `status` is `applied` (the brief changed), `clarification` (a question back, no change) or `unsupported` (can't be done in the brief, no change).
  - `assistantMessage.changedFields`: which brief fields changed, e.g. `["hook", "keyPoints"]` (worked out by the server by comparing the brief before and after, not by the AI). An addition to `ChatMessage` for the idea thread.
  - `brief`: the brief now (unchanged for `clarification` / `unsupported`); `project` because the title may have followed it.
- **Idempotent** (API Design §9; unique `{projectId, clientMessageId}` already exists):
  - the same `clientMessageId` and the same `content` again → the stored result with `Idempotent-Replayed: true`; no AI call, nothing counted;
  - the same `clientMessageId` with other `content` → `422 IDEMPOTENCY_KEY_REUSED`;
  - while the first one is still being answered → `409 RUN_IN_PROGRESS`;
  - a message that failed (AI busy) can be **re-sent with the same id**: it runs again.
- **Limit:** one unit of the shared `ideas` limit (150/day) per message; given back when nothing is delivered (busy, unusable reply, video moved on or deleted). Refusals and safety blocks count.
- **Errors** (as F2.3): `409 INVALID_STATE` outside the Idea stage (before and after the call; refunded after), `422 UNSAFE_CONTENT` (field `message`, our own sentence), `429 LIMIT_REACHED`, `503 AI_BUSY` (or "unavailable"), `404` for an unknown or someone else's video.

### `GET /api/v1/projects/{id}/idea/chat?limit&cursor`

Oldest → newest (API Design §13.3), `limit` 1–100 (default 50), cursor pagination like the Library. Failed messages are included (status `failed`), so a reload can offer "Send again". The project page also loads the newest 50 on the server, so the thread shows without a second request.

### Storage (`chat_messages`, DB Design §4.5)

- **User message:** `thread: "idea"`, `role: "user"`, `content`, `clientMessageId`, `status: processing → applied | clarification | unsupported | failed`.
- **Assistant message:** `role: "assistant"`, `content` (its reply), `status` as above, plus `changedFields` and `briefAfter` (the brief it produced, so a replay returns exactly what the first answer did).
- **Saved together:** the new brief, the title rule, the user message's status and the assistant message go in **one transaction**, after the AI call (DB Design §6: no external calls inside a transaction). The other 2 angles stay as they were (Q2).
- No migration: the collection, its validator (`content` 1–4,000) and both indexes are in `001_initial_schema`. Account deletion already deletes `chat_messages`.

## AI call (`packages/ai/src/idea-chat.ts`)

- **`refineBrief(input)`**, through `generateJson` (the provider chain, repair round, fall-through, logging with task `idea_chat`).
- **Prompt inputs:**
  - the **current brief** (all fields, as data);
  - the **last 10 messages** of the thread (each cut to 1,000 characters), so "make it shorter" or "the second one" has context;
  - the **new message**;
  - the video's language, length, audience, board or exam, and the creator's "what I teach";
  - **for a brief made from notes** (it has `sourceNotesSummary`): the saved notes too, so "use the part about respiration" works; then the 25 s notes deadline applies. Otherwise 15 s.
- **Data, not instructions:** the brief, the messages and the notes go inside `<brief>`, `<chat>`, `<message>` and `<notes>` blocks with angle brackets neutralised (`asData`). The system prompt says the user's message is a request about the brief only: instructions to ignore the rules, change the output format or reveal the prompt are treated as `unsupported`.
- **Reply** (Zod, one repair round): `{ status: "applied" | "clarification" | "unsupported", reply, brief? }`.
  - `reply`: 1–2 sentences, in the language the user wrote in (Hindi, English or Hinglish), at most 400 characters;
  - `brief`: the whole updated brief (same shape and rules as F2.3/F2.4: key points 3–4 for 60 s, 4–5 for 90 s, in the video's language), required for `applied`, left out otherwise;
  - or a refusal `{ refused: true, category }` as before.
- **Rules in the prompt:** change only what was asked and keep the rest word for word; stay one teachable focus; a notes brief stays inside the notes; asking for another video language, length, voice or style → `unsupported`, pointing to the settings panel (the brief follows the video's settings); "make it longer than 90 s" → `unsupported`.
- **Mock mode:** a sample reply marked `[Mock]` that changes the hook (and adds "for kids" to the audience when the message says kids); `[mock:refuse]` / `[mock:busy]` work; `[mock:ask]` gives a `clarification`.

## The page (`components/idea-step.tsx`)

- **Chat panel** under the brief card (and its other angles): the thread (user right, assistant left; failed messages with **Send again**), a text box (Enter sends, Shift+Enter new line, counter 1,000) and **Send**.
- **Sending:** the message shows at once as "sending…"; on success the brief card updates and the changed fields get a highlight (a cyan outline and a "changed" tag, also announced to screen readers) until the next message. On an error the message stays with the error and **Send again** (same `clientMessageId`).
- **Shared with the rest of the Idea step:** one AI request at a time ("Thinking…"), the daily limit lock, the error texts.
- **Drafts:** the box's text is kept in `localStorage` per video (`vz:idea-chat-draft:<projectId>`), cleared once sent; reads and writes are wrapped so a blocked storage never breaks the page.
- **Read-only** outside the Idea stage (the thread still shows).

## Built (2026-10-19)

- **AI:** `packages/ai/src/idea-chat.ts` (`refineBrief`, `IdeaChatReply`, `changedBriefFields`); temperature 0.5 (edits, not new ideas). A `clarification` / `unsupported` answer that carries a brief anyway has it dropped; an `applied` one without a brief gets the repair round. ## Review fixes (2026-10-19)

- **Brief changed while the AI answered:** an answer that changes the brief is saved only if the brief it was based on is still the current one (same `briefUpdatedAt`, checked inside the transaction). Otherwise nothing is written, the request is refunded and the message marked failed: `412 PRECONDITION_FAILED` ("The brief changed while the AI was answering… Send the message again"). This covers another tab's chat message, a new brief and a switched angle; before, the second save silently undid the first. A question back or an "unsupported" answer doesn't change the brief, so it's still saved.
- **A save that throws** (a transaction error) is refunded and marks the message failed, so it can be sent again at once instead of getting 409 for 2 minutes.
- **A message left "processing"** by a request that died shows as `failed` once stale (2 minutes, the same rule that lets a resend take it over), so the page offers **Send again**. A fresh one from another tab shows "being answered…".
- **Replays** return the brief as it is now with its own `briefUpdatedAt`, never the older brief from the first answer.
- **A notes brief's summary** always stays as it was: it describes the notes, and the highlight doesn't cover it.
- Checked and fine: everything the user wrote, earlier messages included, goes in as delimited data; the AI can change only the brief's fields (`trimBrief` whitelists them, `changedFields` is worked out on the server); every query has the user's id; the claim is idempotent on `{projectId, clientMessageId}` (unique index from migration 001).
- Still true: a request that dies after the AI call doesn't get its unit back (nothing runs to give it back); sending the message again later costs one more.
